Sesi 4 · retrieval

Retrieval: memilih delapan chunk yang tepat

Inilah 80% pekerjaan RAG. Kalau chunk yang benar tidak masuk daftar, model terbaik pun hanya bisa mengarang dengan lancar. Sesi ini membuat retrievalmu bisa diperiksa, bukan dipercaya.

±15 menit Prasyarat: Sesi 3 Hasil: endpoint /search yang bisa diaudit

1 · Satu embedding, satu query

const { data } = await env.AI.run("@cf/baai/bge-m3", {
	text: [question],
});

const { matches } = await env.INDEX.query(data[0], {
	topK: 20,
	returnMetadata: "all",
});

Ambil 20, bukan 5. Alasannya: peringkat pertama sering benar, tapi chunk yang menyelamatkan jawaban sering ada di posisi 8–15. Reranker di langkah 4 akan memangkasnya kembali.

returnMetadata: "all" memberi metadata lengkap, dengan konsekuensi topK dibatasi 50. Kalau kamu hanya butuh field yang terindeks, "indexed" lebih murah dan tidak menambah latency.

2 · Mengambil teks, menjaga urutan

Vectorize mengembalikan ID dan skor, bukan teks. Teksnya ada di D1. Jebakan kecil: WHERE id IN (...) tidak menjamin urutan hasil, jadi urutkan ulang berdasarkan skor dari Vectorize.

const ids = matches.map((m) => m.id);
const placeholders = ids.map(() => "?").join(",");

const { results } = await env.DB.prepare(
	`SELECT id, source, chunk_index, text
	 FROM chunks WHERE id IN (${placeholders})`,
)
	.bind(...ids)
	.all<{ id: string; source: string; chunk_index: number; text: string }>();

const byId = new Map(results.map((r) => [r.id, r]));

const candidates = matches.flatMap((m) => {
	const row = byId.get(m.id);
	return row ? [{ ...row, score: m.score }] : [];
});

3 · Filter metadata

Filter menyempitkan kandidat sebelum top-K dihitung. Artinya filter bukan sekadar kosmetik: ia mengubah chunk mana yang bisa menang.

const { matches } = await env.INDEX.query(data[0], {
	topK: 20,
	returnMetadata: "all",
	filter: { source: { $in: ["catatan/rag.md", "catatan/cloudflare.md"] } },
});
OperatorArtiContoh
$eqSama dengan{ source: "a.md" }
$neTidak sama{ tag: { $ne: "draft" } }
$inTermasuk salah satu{ source: { $in: ["a.md","b.md"] } }
$gte / $ltRentang angka atau prefix string{ tahun: { $gte: 2024 } }

Dua batasan yang sering menggigit: hanya 10 properti yang bisa diindeks per indeks, dan hanya 64 byte pertama tiap string yang bisa difilter. Simpan path pendek.

Untuk isolasi per pengguna, namespace lebih tepat daripada metadata: filter namespace diterapkan lebih dulu, dan satu indeks bisa punya puluhan ribu namespace. Metadata tetap dipakai untuk penyaringan yang lebih kaya di dalam satu namespace.

4 · Reranking: dari 20 jadi 6

Embedding adalah bi-encoder: dokumen dan pertanyaan di-embed terpisah, lalu dibandingkan. Cepat, tapi kehilangan interaksi halus antar kata. Reranker adalah cross-encoder: ia membaca pertanyaan dan chunk bersamaan, jadi jauh lebih akurat — dan jauh lebih lambat per pasangan.

Karena itu polanya selalu dua tahap: ambil banyak dengan cara murah, saring dengan cara mahal.

const { response } = await env.AI.run("@cf/baai/bge-reranker-base", {
	query: question,
	contexts: candidates.map((c) => ({ text: c.text })),
	top_k: 6,
});

// Item respons merujuk ke indeks pada array contexts.
const top = response
	.map((r) => ({ ...candidates[r.id], rerankScore: r.score }))
	.sort((a, b) => b.rerankScore - a.rerankScore);

Biayanya $0,003 per juta token — untuk 20 chunk pendek, praktis nol. Waktu tambahannya ratusan milidetik. Itu trade-off yang hampir selalu layak.

Periksa sekali

Bentuk item respons bisa berbeda antar model. Jalankan sekali dengan console.log(response) dan pastikan field-nya sebelum mengandalkan pemetaan di atas.

5 · Hybrid search: saat kemiripan makna tidak cukup

Vectorize hanya melakukan pencarian vektor. Ia tidak punya BM25. Akibatnya, query seperti "error 1102", "SK-2024-117", atau "fungsi toMarkdown" bisa meleset: token yang sangat spesifik tidak punya "makna" yang kuat untuk di-embed, justru butuh kecocokan literal.

Solusinya menggabungkan dua daftar peringkat. Cara paling sederhana dan tahan banting: reciprocal rank fusion.

function rrf(lists: string[][], k = 60) {
	const scores = new Map<string, number>();
	for (const list of lists) {
		list.forEach((id, i) => {
			scores.set(id, (scores.get(id) ?? 0) + 1 / (k + i + 1));
		});
	}
	return [...scores.entries()].sort((a, b) => b[1] - a[1]);
}

RRF hanya butuh urutan, bukan skor — jadi kamu tidak perlu menormalkan skor cosine (0–1) dengan skor BM25 (tak terbatas). Itu sebabnya ia jadi default di banyak sistem.

Untuk daftar kedua, ada dua pilihan:

PilihanKelebihanKonsekuensi
D1 FTS5 (SQLite full-text)BM25 asli, satu databaseDukungan virtual table di D1 perlu diuji di akunmu — coba CREATE VIRTUAL TABLE ... USING fts5 di database percobaan dulu
Skor kata kunci sederhanaPasti jalan: hitung irisan token di kandidat teratasHanya menyaring kandidat yang sudah lolos vektor, bukan mencari di seluruh korpus

Jangan mengarang dukungan

Sebelum memakai FTS5, buktikan dulu di database percobaan. Kalau perintah CREATE VIRTUAL TABLE ditolak, jangan paksakan — pakai skor kata kunci sederhana dan lanjut. Yang penting: hybrid bukan syarat, ia perbaikan opsional setelah kamu punya data evaluasi.

6 · Ambang skor: jangan menebak

Pertanyaan pertamamu mungkin: "skor berapa yang dianggap relevan?" Jawaban jujurnya: tidak ada angka universal. Distribusi skor bergantung pada model embedding, panjang chunk, dan korpusmu.

Cara yang benar: jalankan 20 pertanyaan dari golden set-mu, catat skor chunk yang benar dan chunk yang salah, lalu lihat apakah ada celah. Kalau skor benar semua di atas 0,62 dan yang salah di bawah 0,55, ambang 0,58 masuk akal. Kalau tumpang tindih, ambang tidak akan menolong — perbaiki retrieval-nya.

7 · Latihan

  1. Buat endpoint GET /search?q=... yang mengembalikan 6 chunk teratas: id, source, chunk_index, score, rerankScore, dan 120 karakter pertama teks.
  2. Untuk 10 pertanyaan dari eval/questions.md, catat: apakah file sumber yang benar muncul di top-20? Apakah masih muncul setelah rerank jadi 6?
  3. Tulis dua angka: hit@20 dan hit@6. Itu baseline retrieval-mu.
Hasil sesi ini

Kamu bisa melihat persis chunk apa yang terambil untuk sebuah pertanyaan, dan punya dua angka baseline yang akan dibandingkan setiap kali kamu mengubah chunking atau reranker.

8 · Cek pemahaman

Dari memori: kenapa filter metadata mengubah hasil lebih dari sekadar "menyembunyikan" hasil yang tidak relevan?

Karena filter diterapkan sebelum top-K dihitung. Chunk yang tersembunyi tidak lagi mengambil slot di 20 besar, sehingga chunk relevan dari sumber lain bisa naik. Kalau filter diterapkan setelah top-K, kamu bisa mendapat 20 hasil yang semuanya tersaring habis.

2. Kenapa mengambil 20 chunk lalu menyaringnya jadi 6?

3. Query jenis apa yang paling butuh hybrid search?

4. Dari mana angka ambang skor yang layak berasal?
